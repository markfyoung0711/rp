Demo runbook: the leasing-outreach bot

What you type, what you show and what you say, in order. The bot is a command-line tool: records in, one decision per record out. Template mode is free, offline and deterministic.

Deadline 12:00 noon CT, Sep 24 Hold-out: 12 unseen records v0.3 · learns its rules from examples $0 API cost by default

Start here: read this aloud

It’s fine to read from this page; everyone does. Slow down, pause after each command, and let the screen do the talking. If you lose your place, say “let me show you that on screen” and run the next command.
1 · Opening: read this first

“Before I start: I’ve planned about twelve minutes in five parts. First, the four decisions you asked for, on your samples. Then your twelve hold-out records. Then how the bot learns its rules. Then where the AI fits. And last, a decision table with a policy question for you.”

“Do you want to go in that order, start with the hold-out, or is there something you’d like to see first?”

“Go ahead”Read part 1 below. “Hold-out first”Go to part 2 (the hold-out). After it, say: “Now let me show you why those outputs look the way they do,” and come back to part 1. “We have questions”Answer each in one sentence, then run the matching command from the test table or the cheat sheet.
2 · What it is: read before the first command

“This is a decision bot for leasing outreach. For each record, it decides whether to contact the person, on which channel, when, and what to say, plus the next step.”

“Everything that’s legal or compliance-related (consent, opt-out, timing, fair housing) is decided by code, so it’s guaranteed and explainable. The rules are learned from your labelled examples. AI is optional and only writes the wording.”

“Let me start with your two samples.”

Before the interview

During the demo: five parts, about 12 minutes

  1. What they said they’d test: the four decisions

    The assignment: read each record, decide whether to communicate, how, and what to say, with output that semantically matches the expected result.

    uv run bot.py -i plans/sample.jsonl --compare

    Point at: ✅ on channel, send time, subject, body, CTA and next action for both samples; the “why” list under each; RUN STATS: “Controllable fields … all match: 2/2”, latency PASS, safety PASS, PII leaked 0, cost $0.

    Say, after the samples run

    “Here’s the output for both samples. Each green check is a field compared with your expected answer: channel, send time, subject, message, call to action and next action. They all match.”

    “Under each record is a ‘why’ list. For Taylor: SMS, because it’s Taylor’s first preferred channel and there’s consent for it. Nine a.m. the next day, because nine had already passed at the last contact. And a short welcome sequence, because the move-in is 32 days away.”

    “At the bottom, the run stats: speed, safety checks, personal data withheld, and cost: zero.”

    “You’ll notice ‘learned from 2 labelled examples’. The rules came from your two samples, and I’ll show you how in part 3.”

    Say, before the no-consent case

    “Now the ‘whether’ decision. This person hasn’t consented to any channel.”

    uv run bot.py -i tests/edge_cases.jsonl --only no_consent
    Say

    “No message, and it says why: no channel with consent. It never guesses.”

    Optional extras: --only kids (fair housing), --only MNT (an unfamiliar record type).

    Required states: RUN STATS shows Req. states: consent_verified 2/2, fair_housing_check_passed 2/2, brand_style_applied 2/2: PASS. The samples require all three; the spec only defines the first two.

    sed -n '/^brand_default/,$p' config/rules.yaml && sed -n '/  brand:/,$p' config/properties.yaml
    Say

    “Your samples require a brand_style_applied state, but nothing defines it. To model the branding state, I derived this configuration file that applies branding rules: the name the property goes by, banned sales phrases, no emoji or shouting, and length limits. There are defaults for any property, and each property can override them. Every message is checked against it, AI wording that breaks it falls back to the template, and each output reports the state as verified.”

  2. The hold-out: their 12 records

    They send a file

    Save it with “holdout” in the name (it also blocks learning from it):

    uv run bot.py -i holdout.jsonl -o out/holdout.jsonl --answer-only --compare

    They paste text

    Paste, then Ctrl+D. JSONL, a JSON list or chat-style text all work.

    uv run bot.py --paste -o out/holdout.jsonl --answer-only --compare

    Hand over: out/holdout.jsonl, or copy the block between === BEGIN OUTPUT === and === END OUTPUT ===. --answer-only makes that exactly their expected shape: task_id, next_message, next_action, one line per record. The screen still shows every reason and RUN STATS to talk through. If their records include expected, --compare gives a live score per field. If they want their own file back with answers filled in, use --fill-expected instead (their expected is kept as expected_original).

    Commands for each option

    If they want a match to their expected format (answers only, one line per record) ...

    uv run bot.py -i holdout.jsonl -o out/holdout.jsonl --answer-only --compare

    If they want their own input file back, with our answer filled in as expected ...

    uv run bot.py -i holdout.jsonl -o out/holdout_filled.jsonl --fill-expected --compare

    If they want the full output, with the reasons (why) and meta ...

    uv run bot.py -i holdout.jsonl -o out/holdout_full.jsonl --compare

    If they want it easy to read, one field per line ...

    uv run bot.py -i holdout.jsonl -o out/holdout_pretty.json --answer-only --pp

    If they want only the JSON on screen, to copy and paste ...

    uv run bot.py -i holdout.jsonl --answer-only --quiet

    If they ask about one record (put part of its task_id after --only) ...

    uv run bot.py -i holdout.jsonl --only TASK_ID_TEXT

    If they paste the records instead of sending a file (paste, then Ctrl+D) ...

    uv run bot.py --paste -o out/holdout.jsonl --answer-only --compare

    If they give a reference “now” time, so no send lands before it ...

    uv run bot.py -i holdout.jsonl -o out/holdout.jsonl --answer-only --now 2025-12-08T12:00:00-06:00

    If they want AI wording (paid, about $0.004; only with your OK, capped at 5 cents) ...

    uv run bot.py -i holdout.jsonl -o out/holdout_llm.jsonl --answer-only --llm --budget 0.05
    Say

    “Twelve unseen records, one decision each, exported in the same shape as your expected answers. The reasons are on screen if you want to go through any of them. Nothing was tuned to these; it never learns from a hold-out.”

  3. Learning mode: rules learned from labelled examples

    uv run learn.py plans/sample.jsonl --eval

    Point at: each rule with its evidence (send hours, dayN offset 2/2, horizon threshold 50 days); leave-one-out 0/2: one example can’t teach the other, which proves the rules come from the data.

    uv run learn.py plans/sample.jsonl tests/labelled_extra.jsonl --eval

    Two more examples → the rules change (threshold 50 → 36, open +3 → +2 days) and both samples are predicted correctly.

    cp plans/sample.jsonl /tmp/holdout.jsonl && uv run learn.py /tmp/holdout.jsonl

    It refuses anything named “hold”: no training on the test set.

    Say

    “Learning is offline and versioned, like training a model. The bot at runtime applies config/learned.yaml. More labelled data means better rules, and I can measure it.”

  4. Template vs LLM wording, both using the learned rules

    uv run bot.py -i plans/sample.jsonl --compare

    Template mode: RUN STATS says Rules: … learned from 2 labelled example(s); wording is exact, free, offline.

    uv run bot.py -i plans/sample.jsonl --llm --compare

    Cost guard: it stops before spending and shows the calls, tokens and dollars avoided.

    uv run bot.py -i plans/sample.jsonl --llm --compare --budget 0.05

    With a 5-cent budget (about $0.004 for the two samples): Claude writes the sentence; channel, time, CTA and next action are identical (the same learned rules); body similarity drops from 100% to a paraphrase. Run it once before the interview and re-runs are cached at $0.

    Say

    “Same learned decisions in both modes. The model only phrases one sentence from allow-listed facts, its output goes through the guards, and it can never spend money without a limit.”

  5. The decision table, and what an SME must decide

    uv run python scripts/decision_table.py --sme

    Point at: all 120 consent × channel-preference combinations run through the bot and checked against the written policy: 120/120, never sends without consent. The 30 no-sends each have a precise reason. Then the 15 rows for SME review: someone consented to a channel that isn’t in their preference list.

    Full table to share: plans/decision-table-channel.md (renders on GitHub).

    Say

    “I didn’t sample the channel logic, I enumerated it. It’s right for every case, and it surfaced a policy question I shouldn’t decide alone: if someone consented to email but only listed SMS, do we email them? Today we respect the preference list. That’s your call.”

Then: state the assumptions below, and open plans/solution.md for what’s designed but not built.

AI wording and cost

Assumptions to say out loud

Where the spec was silent, these are the choices I made. Practise reading them once before the interview; in the demo, say them before you’re asked.

  1. Send time = last contact + the day number in the task ID, at 09:00 for SMS, 10:00 for email or voice, moved to the next day if already past. Inferred from two samples; configurable.
  2. Channel = the first preferred channel with consent. Voice sends an automated call script; its shape is inferred, because the samples show none.
  3. Next action: a new lead starts a welcome sequence: the short one if move-in is within 50 days, the long one otherwise. Anyone else gets a follow-up in 3 days. The 50-day cutoff is learned from the samples, where a 32-day lead got the short sequence and a 68-day lead got the long one.
  4. Property details (tour days, amenities, links) come from one config file, never invented. An unknown property gets a generic message, the default brand, and a flagged configuration gap.
  5. Brand style isn’t defined in the spec, so I modelled it as a per-property brand profile with a check on every message.
  6. Language: the recipient’s, if the property offers it; otherwise the property’s default. English, Spanish and French templates exist; Arabic (right-to-left) and Hindi are drafts flagged for native-speaker review. SMS in those scripts is limited to 210 characters, and English STOP always works.
  7. No-send shape (next_message: null plus a reason) is my choice; the spec doesn’t define one.
  8. Personal data: only the first name, in the greeting. task_id is the only join key; identity belongs to the system of record.

Likely gotchas and quick answers

They askYou answer
“Is this an AI agent?”“An autonomous decision pipeline. Compliance-critical decisions are deterministic code; a model may write only the wording.”
“Is it really learning?”Run L1 and L3: the rules are learned from labelled examples with evidence, change when examples are added, and are measured by leave-one-out. In --llm mode the wording is also learned in context from the samples.
“A record type you’ve never seen?”Levels 1–3: new values hit default rows; odd formats are repaired and noted; unknown shapes are searched for fields, with confidence low. No consent → never send.
“What about PII?”“Only the first name leaves the bot. Twenty rental-PII categories are tested: 81 withheld, 0 leaked. Balances and account numbers never go in a message.”
“What if Anthropic is down?”“Template mode never calls it. With --llm, each record falls back to the template; decisions are identical.”
“100,000 records?”“52 s in template mode at $0. With --llm, about $170 on Haiku, or $85 via the Batch API; the bot shows that and stops first.”
“Change a rule live?”“Rules live in config/rules.yaml: one row, re-run.”

If something looks wrong: fix it live with Claude Code

They may throw a bad record at it on purpose. A calm, methodical fix is a strong demo, and it shows how you work with an AI coding assistant.

  1. Name it

    Say

    “Interesting, let’s see what the bot says about it.”

  2. Read the bot’s own explanation

    Most surprises aren’t errors: a no-send always has a reason, and warnings say what was repaired or assumed. Isolate the record:

    uv run bot.py -i holdout.jsonl --only <task_id>

  3. Capture it

    uv run python scripts/report.py holdout.jsonl --only <task_id> --note "expected X, got Y"

    Prints a paste-ready report (version, command, input record, output, stats) and saves out/report.txt. If the bot itself fails, it prints a one-line problem plus this exact command, never a raw traceback.

  4. Paste it into the Claude Code session and fix it together

    In the ~/realpage Claude Code terminal: paste the report and say what you expected. Claude reproduces it, proposes the smallest fix, re-runs the samples and tests, and commits. Most fixes are one row in config/rules.yaml.

    Say

    “This is how I work: the AI does the legwork, but every fix must reproduce the problem first, keep both samples matching, and pass the tests before it’s committed. The same rules I used all morning.”

    uv run python scripts/run_checks.py

  5. If there’s no time to fix

    Say

    “I’d log it and fix it after: here’s the report. The bot failed safely, with no send and a reason, which is the behavior I want when it’s unsure.”
