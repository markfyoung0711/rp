# Retrospective: Spec First, Then Build, Then Refine

> The session of 2026-09-24, from receiving the assignment to demo-ready, reviewed against Mark's motto: **"More time spent on the spec and review means easier generation."** Times are US Central.

## The cadence in numbers

| Phase | Time | What happened | Output |
|---|---|---|---|
| **1. Spec and planning** | ~02:30–03:40 (~70 min) | Captured the assignment; wrote use cases, actors and design; opened issues; started a decision register | 11 plan documents, 10 issues, D-001 to D-021 |
| **2. Independent review** | 03:21–03:52 (~30 min, overlapping) | Two reviewers on different models (Claude Sonnet 5, Gemini), plus a code review of Gemini's reference bot; reconciled into one build spec | `review.md`, D-022 to D-039, **the build spec D-038** |
| **3. Build the core** | 04:02–04:21 (**~20 min**) | Explainer, then the bot: reader, normalizer, decisions, templates, guards, optional AI, command line | **Both samples matched on every field on the first run**; v0.1.0 |
| **4. Refine: harden, question, extend** | 04:24–06:45 (~2 h 20 min) | Checklist fixes, messy input, cost guard, stats, PII, learning, decision table, brand, validator, voice, demo materials | 59 commits total, 56 decisions, 25 tests, 35 automated checks, v0.3.0 |

**The shape:** about 1 h 40 min of spec and review, **20 minutes to generate a working core**, then about 2 h 20 min of refining.

## Did the motto hold? Yes, with one qualification

**What the spec and review phase bought:**
- **The core was generated in about 20 minutes and was right on the first run.** Both samples matched every field, including the exact message text. That happened because D-038 had already settled every decision: the pipeline order, what's code vs AI, the send-time rule, the output shape, the "done when" criteria.
- **The reviews caught the one bug that would have sunk the demo, before any code existed.** Our reading of the send time ("everything sends on a shared 'today'") was wrong. Review 1 (F-01) found it with arithmetic, and the corrected rule (last contact + dayN, rolled forward) is why sample 1's send time came out right.
- **Two reviewers on different models were worth more than one.** They agreed on the core (stateless batch, code decides, AI writes), which gave confidence. Where they differed, the gaps showed: review 2's own "day0 = +0" arithmetic was wrong, and its reference bot failed sample 1 and used a retired model. Reconciling them produced a better spec than either alone.
- **Decisions stayed traceable.** Every later change had a D-number to point at, and "why does it do X?" always had an answer.

**The qualification: much of the early spec was scope creep.** The first plan designed a platform: database, a three-pane UI, sentiment tracking, review-site ingestion, adjacent agents. **None of it was built, and the reviewers were right to cut it.** The spec time that paid off was the time spent narrowing to the graded core and getting it reviewed; the time spent widening the platform mostly became roadmap material and talking points. A sharper version of the motto: **"More time on the *right* spec, independently reviewed, means easier generation."**

## The refining phase: where the quality came from

The build took 20 minutes; making it trustworthy took more than two hours. Almost all of that came from **your questions**, most of them plain "what if?" or "what is this?" questions. Many of them found real gaps that no spec had anticipated:

| Your question or action | What it uncovered | Fix |
|---|---|---|
| "is there any PII test we can run?" | A rejected first name (an email or SSN typed into the name field) was **echoed into the output** | Never echo it; planted-PII tests; 20 rental-PII categories |
| Fed in a screenshot | A PNG was misread as UTF-16 and produced a **fake record** | Detect file types by their first bytes; clear refusal |
| "do not incur a cost at all" | Nothing stopped an accidental paid run | Cost guard, then a loud stop with dollars avoided, then `--budget` |
| "does learn.py do the same input protections?" | It crashed on bad input and would have **learned poisoned labels** | Same protections plus label validation |
| "should it run against the hold-out?" | Nothing stopped training on the test set | `learn.py` refuses any file named "hold" |
| "what is brand_style_applied?" | A required state that the samples demand was **undefined and unchecked** | Brand profile, brand guard, required states reported |
| "rules.yaml was generated by you…" | **No validation of the rules at all**; a typo could break the legal window | Rules validator; the bot refuses invalid rules |
| "is voice one of their options?" | A hold-out voice case would be a **guaranteed miss** | Voice channel with a call script |
| Decision table request | Every no-send claimed "no consent", even where voice was consented; an SME policy question | Precise reasons; 11 rows flagged for an SME |
| Reading 12 blind outputs by eye | "a early‑February move", a phrase repeated in one message | Wording fixes the automated checks couldn't catch |

**The pattern that worked:** a question → probe it with a real run or a planted test → find the gap → fix it, add a test, update the docs, record a decision. Questions from someone who says they are "a novice at bots" proved to be excellent adversarial testing, because they don't assume the system already works.

## The back-and-forth: what helped and what cost

**What helped**
- **Short, specific requests** ("--pp", "add the budget option", "put it in the cheat sheet") could be done and verified in minutes.
- **"Why" questions before "do" questions.** Asking what template mode, CTA, p95 or a hold-out *is* led to better decisions and better demo material (the field guide, cheat sheet and explainer).
- **Insisting on proof.** "To prove, run:" commands, the diff demo and the decision table all turned claims into things you can show on screen.
- **Constraints stated plainly** ("do not incur a cost", "fail loudly", "don't show my AI questions") produced clean designs: the cost guard and the separate audience-facing page.

**What cost**
- **Keeping documents in sync.** Every change rippled through the README, four web pages, the cheat sheet, the field guide, the decision register and `solution.md`. The runbook reached version 14. Generating pages from Markdown sources helped; a single command to regenerate everything would help more.
- **Interleaved requests mid-task.** Several follow-ups arrived while a change was half-done. It worked, but it caused re-runs and one stale claim (the check count) that had to be chased down.
- **My own mistakes, caught late:**
  - I overclaimed "under 1 ms"; the first record takes about 10 ms.
  - I swept your scratch `a.json`/`b.json` into a commit with `git add -A`.
  - A shell quoting slip mangled an issue body.
  - I made small paid API calls before you said no cost.

  Each was caught and fixed, but they're a reminder to check claims against a real run before writing them down, and to stage files deliberately.

## Lessons to carry forward

1. **Spend the spec time narrowing, not widening.** Write the graded core and its "done when" first, and get it reviewed before building. Park the platform as a roadmap.
2. **Use independent reviewers on different models, then reconcile.** Where they disagree is where the risks are.
3. **Expect generation to be fast and refinement to be most of the work.** Budget for it.
4. **Treat plain questions as tests.** "What is X?", "what if Y?" and "does Z also do W?" found more real defects than any checklist.
5. **Make every claim provable** with a command, and keep derived documents generated from one source.
6. **Freeze deliberately.** New features close to a deadline (voice, validator) went well because each shipped with tests and a green check run; that discipline is what makes late changes safe.
